## 1. Разделение ролей: дизайнер и настройщик

**Ситуация.** При переносе на VPS дизайнер работает самостоятельно в любое время, не рискуя сломать систему. При запросах на настройку агент отказывает и направляет к настройщику.

Прямой доступ по API-ключу заблокирован (429 после потери контекста в Telegram-мосте). Нужен способ работы с макетами без постоянного подключения к сервису Figma.

**Ситуация.** Применяется при каждой задаче, где есть макет Figma. Особенно критично при переносе проекта на VPS (см. пункт 2) — без альтернативы перенос невозможен.

- [ ] Проверить, может ли агент обработать экспортированный файл (структура, токены, ассеты) без MCP-подключения
- [ ] Оценить figma-developer-mcp с лимитированным/отложенным доступом (кэш, throttle, чтобы избежать 429)
- [ ] Рассмотреть сторонние инструменты экспорта (плагины Figma, CLI)
- [ ] Протестировать гибрид: экспорт файла дизайнером → загрузка агентом → обработка без подключения

## 8. Выгрузка результатов работы агента в Figma (HTML → Figma)

**Зачем.** Агент верстает HTML-прототип, но дизайнер работает в Figma. Нужен способ загрузить прототип агента обратно в Figma как редактируемые слои — чтобы дизайнер мог дорабатывать его как родной макет, а не перерисовывать.

**Что пробовали.** Рассмотрели 3 пути: (1) SVG-файл — простой, но плоский (нет Auto Layout/Components); (2) плагин [html.to.design](https://www.figma.com/community/plugin/1159123024924461424) — вставка HTML → слои с Auto Layout; (3) собственный плагин через Figma Plugin API — максимум структуры, но требует написания кода и настройки.

**Результат.** Выбрали путь №2 — плагин html.to.design. Дизайнер устанавливает плагин в Figma, вставляет HTML-прототип агента → получает редактируемые слои с Auto Layout, текст-стилями, компонентами. Бесплатно, даёт ~80% структуры. **Проверили — работает.** Полный разбор вариантов в `_tasks/2026-07-23__ettn-flyer/result/figma-import-options.md`.

**Ситуация.** Применяется, когда агент отдал HTML-прототип, а дизайнеру нужно продолжить работу в Figma (доработка, передача команде, согласование с заказчиком).

**Статус:** проверено, работает
- [x] Исследовать варианты импорта HTML в Figma (SVG, плагин html.to.design, Figma Plugin API)
- [x] Протестировать плагин html.to.design на HTML-прототипе флайера ЭТН
- [ ] Описать рабочий процесс в skill/инструкции для дизайнера (шаги установки плагина, вставка HTML, что дорабатывать вручную)
- [ ] Прогнать на нескольких прототипах — собрать список ограничений html.to.design (что не переносится из HTML)
- [ ] Оценить путь №3 (собственный плагин Figma Plugin API) для задач, где нужна полная структура с Variables/Components

## 5. Полноценная работа дизайнера с агентом через Telegram

**Зачем.** Сейчас Telegram-мост работает в основном в одну сторону — агент отправляет готовые файлы и отчёты дизайнеру. Нужно двустороннее взаимодействие: дизайнер ставит задачи, уточняет запросы, получает промежуточные вопросы от агента — всё через Telegram, без необходимости открывать терминал opencode.

**Ситуация.** Удалённая работа дизайнера, работа с телефона, передача задач «на ходу». Особенно критично после переноса на VPS — если дизайнер не имеет SSH-доступа или не хочет работать в терминале.

**Статус:** идея
- [ ] Проанализировать текущий telegram-bridge: что умеет, чего не хватает для двусторонней работы
- [ ] Продумать сценарии: постановка задачи, уточнение, вопрос агента → ответ дизайнера, подтверждение отправки результата
- [ ] Оценить сохранение контекста диалога через Telegram (связка с design-memory)
- [ ] Протестировать запуск новой задачи из Telegram → создание папки в `_tasks/` → выполнение → уведомление

## 6. Инструментарий для работы с графикой

**Зачем.** Агент не «видит» картинки — не может анализировать макеты, референсы, эскизы, скриншоты визуально. Сейчас работа с графикой идёт через текстовые описания и MCP Figma (токены/структуру), но этого недостаточно для задач, где важна визуальная оценка: сравнение референсов, анализ компоновки эскизов, оценка скриншотов интерфейса.

**Ситуация.** Любая задача с визуальным референсом (скрин сайта, эскиз от дизайнера, фото макета). Без инструментов работы с графикой агент опирается только на текстовое описание от дизайнера, что снижает качество и скорость.

**Статус:** идея
- [ ] Исследовать способы передачи изображений в модель: vision-модели, MCP для OCR/анализа изображений, конвертация в описание
- [ ] Проверить, поддерживает ли текущая модель (`ollama/glm-5.2:cloud`) ввод изображений
- [ ] Рассмотреть MCP-серверы для анализа графики (описание изображения, извлечение текста, сравнение)
- [ ] Оценить связку с UX-исследователем: референс-скрин → анализ → сравнение с паттернами
- [ ] Протестировать сценарий: дизайнер присылает эскиз → агент анализирует компоновку → предлагает варианты

## 7. Skill/субагент для вёрстки прототипов по требованиям фирмы

Сейчас агент верстает «в целом правильно», но без учёта внутренних конвенций команды. Skill/субагент с чек-листом правил сделает вёрстку предсказуемой и снимает правки от вёрстки.

**Ситуация.** Применяется при любой задаче, где на выходе HTML-прототип (лендинг, флайер, вариант интерфейса). Skill активируется при сборке финального HTML и проверяет результат по чек-листу перед отдачей дизайнеру.

## 9. Шаблон проекта для коллег (boilerplate)

**Зачем.** Создать готовый к развёртыванию шаблон проекта на базе текущей конфигурации, которым коллеги могут развернуть у себя: клонировать → запустить setup → вставить свои ключи → работать. Не skill, а boilerplate-репозиторий.

**Ситуация.** Коллеги-дизайнеры или другие команды хотят аналогичного ассистента. Сейчас развёртывание требует ручной настройки — никто не сможет повторить без знания всех деталей проекта.

**Факторы, мешающие реализации:**
- **Figma MCP** — главный блокер. Требует Figma Desktop + платную подписку (~25 €/мес). Не у всех есть. Без него проект теряет половину ценности. Разблокируется планом №4 (работа через экспорт файла).
- **`.env`** — у каждого свои ключи (Tavily, Figma, Telegram). Решается `.env.example`.
- **Платформы** — пути Windows vs Linux в `opencode.json`. Решается setup-скриптом с автоопределением ОС.
- **Telegram-бот** — каждому нужен свой бот + chat ID.
- **Рабочие данные** — нужно вычистить `_tasks/`, `design_memory.db`, `.venv/` из шаблона.
- **Node.js** — для npx MCP-серверов.

Подробный анализ: [`_system/boilerplate-analysis.md`](_system/boilerplate-analysis.md)

**Статус:** идея
- [ ] Дождаться завершения плана №4 (экспорт Figma) — снимает главный блокер
- [ ] Почистить репо от рабочих данных (структура без содержания)
- [ ] Создать `.env.example` с плейсхолдерами
- [ ] Написать `setup.sh` / `setup.bat` (venv, deps, init db, автоопределение ОС)
- [ ] Адаптировать `opencode.json` под автоопределение платформы
- [ ] Написать `DEPLOY.md` — пошаговая инструкция
- [ ] Проверить: клонировать на чистую машину → setup → запустить → тест-задача

## Синхронизация todo.md и README.md

**Зачем.** `_system/todo.md` — рабочие планы настройщика. `README.md` — публичная сводка для репозитория. Планы развития системы отражаются в обоих файлах, но формулировки разные (детальный чек-лист vs краткое описание для внешнего читателя). Нужно держать их синхронизированными, чтобы не было расхождений.

**Ситуация.** При любом изменении статуса идеи/плана в `todo.md` — проверить и обновить соответствующий раздел в `README.md`.

**Статус:** правило (в работе)
- [ ] При обновлении `todo.md` проверять раздел «Планы развития» в `README.md`
- [ ] При добавлении нового пункта в `todo.md` добавлять краткое описание в README (если это не внутренняя техническая деталь)
